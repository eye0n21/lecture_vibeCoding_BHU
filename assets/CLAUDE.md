# CLAUDE.md — 부산보건대 아이디어톤 프로토타입 제작 규칙

이 파일은 강사가 작성한 규칙서입니다. 학생은 이 파일을 수정하지 않습니다.
이 폴더에서 작업하는 Claude Code는 아래 규칙을 항상 따릅니다.

---

## 1. 이 프로젝트는 무엇인가

- 부산보건대학교 "2026 AIDX 기반 부산광역시 지역사회 현안 해결 아이디어톤"의 팀 프로토타입
- 만드는 것: 팀의 아이템을 소개하고, 핵심 기능을 시연하는 웹 페이지
- 제한 시간: 오늘 하루(약 4시간). 먼저 "열리고, 보이고, 눌리는 것"을 확보한 뒤, 남은 시간은 완성도를 높이는 데 씁니다
- 결과물 용도: 오늘 15시 팀 발표에서 심사위원 앞에서 직접 시연

## 2. 시작 신호와 진행 방식

학생이 "claude.md 파일을 읽고 html 페이지 작성 시작해" 또는 비슷한 말로 시작하면, 바로 코드를 만들지 않습니다. 먼저 아래 순서로 진행합니다.

### 2-1. 디자인 방향 정하기 — 세 가지 중 하나
- 먼저 기획서.md가 이미 있으면(이전에 인터뷰를 마친 팀) 읽고 "이어서 진행할지, 처음부터 다시 정할지" 한 번만 묻습니다.
- 폴더에 design.md나 기능명세서.md가 채워져 있으면 먼저 읽습니다. 거기 적힌 내용은 인터뷰에서 다시 묻지 않고, 빈 항목만 묻습니다. 학생이 2일차에 각자 쓴 기능명세서는 팀원 것이 여러 개일 수 있으니, 합쳐서 5개 이내로 고르게 돕습니다.
- 그다음 폴더를 보고, 디자인 방향을 어떤 방식으로 정할지 학생에게 세 가지를 보여주고 고르게 합니다. 폴더 상태로 이미 답이 보이면 "이 방식으로 진행할게요"라고 확인만 받습니다.
  - (A) DESIGN.md 내려받기: getdesign.md에서 마음에 드는 사이트의 DESIGN.md를 받아 폴더에 넣은 경우. 색·글꼴·간격·버튼 모양 같은 시각 규칙만 있고 팀 아이템 내용은 없습니다. 끝까지 읽고 "이 스타일을 따르되 글자 크기는 대상자에 맞게 키우겠다"고 알립니다. 레이아웃은 DESIGN.md의 성격에 맞춰 Claude Code가 제안합니다.
  - (B) 참고 페이지 캡처: 비슷하게 만들고 싶은 페이지의 화면 캡처를 참고 폴더에 넣은 경우. 이미지를 보고 첫 화면 구성, 색, 글꼴 느낌, 섹션 리듬, 카드·버튼 모양을 글로 정리해 DESIGN.md 초안을 쓰고 학생에게 확인받습니다. 그대로 베끼지 않고 "느낌과 구조"만 가져오며, 내용과 색은 팀 아이템에서 끌어옵니다.
  - (C) 대화로 함께 쓰기: 아무것도 없는 경우. 인터뷰 6묶음에서 디자인 질문을 하고, 답을 모아 DESIGN.md를 Claude Code가 작성해 확인받습니다. 파일을 만들어 오라고 돌려보내지 않습니다.
- 어느 방식이든 DESIGN.md는 "시각 규칙", 기획서.md는 "내용"으로 역할을 나눕니다. 두 파일이 모두 있어야 제작을 시작합니다.

### 2-2. 인터뷰
- 인터뷰를 시작하기 전에 먼저 1일차 문제정의서 8번 "최종 문제정의문"을 그대로 붙여 달라고 합니다. 형식은 "[대상자]는(은) [상황]에서 [원인](으)로 인해 [불편]을 경험하고 있으며, 이를 해결하기 위해 [변화]가 필요하다"입니다. 받으면 다섯 칸(대상자 / 상황 / 원인 / 불편 / 변화)으로 쪼개 표로 보여주고 맞는지 확인합니다. 문장이 없으면 다섯 칸을 하나씩 물어 함께 만듭니다.
- 이 다섯 칸이 페이지의 기준입니다. 대상자 = 페이지의 주인공과 말투, 상황 = 첫 화면 바로 아래의 "이런 순간" 장면, 원인 = 문제 섹션(지금의 대처·한계와 나란히), 불편 = 첫 화면 문장의 재료, 변화 = 시연 기능이 보여줘야 할 결과. 시연 기능을 정할 때 "이 기능을 누르면 [변화]가 화면에 보이는가"를 한 번 검사하고, 아니면 학생에게 알립니다.
- 문제정의문 확인이 끝나면 결과물 유형을 셋 중 하나로 고르게 합니다. 기본 추천은 (다)이고, 해결안이 "웹사이트"면 (나), 시간이 빠듯하거나 설명이 더 중요한 팀은 (가)를 권합니다.
  - (가) 소개 페이지: 구현 예정인 앱·서비스의 상세 내용을 한눈에 확인하는 페이지. 흐름은 문제 → 대상자의 하루 장면 → 해결안과 기능 → 화면 모형 → 운영 주체·다음 단계 → 팀. 화면 모형은 휴대폰 틀 안에 주요 화면 2~4장을 그려 넣고 "다음 화면" 버튼이나 탭으로 넘겨 보게 합니다. 기능이 실제로 작동하지는 않지만 넘기기는 눌려야 합니다.
  - (나) 실제 웹서비스 프로토타입: 그 서비스의 웹페이지 자체. 첫 화면에 서비스가 무엇인지 한 문장과 바로 시작하는 버튼, 그 아래는 사용자가 실제로 쓰는 화면(보통 2~3개). 팀·대회·가상 데이터 안내는 풋터에. 문제와 해결 과정 설명은 발표 자료가 맡으므로 페이지에는 길게 쓰지 않습니다.
  - (다) 소개 + 시연 (샘플 「오늘약」이 이 유형): (가)의 소개 흐름에 "시연" 섹션(또는 멀티 페이지면 demo.html)을 더한 것. 시연 섹션에서는 휴대폰 틀(또는 태블릿·키오스크·안내판 틀) 안에서 핵심 기능 1개가 실제로 작동합니다 — 누르면 화면이 바뀌고, 입력하면 결과가 뜹니다. 앱이 아닌 서비스(공간·프로그램·제도)면 신청서·예약·안내판처럼 "사용자가 만지는 화면" 하나를 시연으로 삼습니다.
  - 어느 유형이든 심사표 ③(웹 서비스에 해결 방법이 잘 담겼나, 25점)은 "클릭 2~3번 안에 핵심 장면에 닿고, 그 결과로 [변화] 칸이 보이는가"로 봅니다. 유형은 기획서.md 맨 앞 문제정의문 아래에 적습니다.
- 2묶음(대상과 문제)은 이 다섯 칸으로 이미 채워진 항목은 묻지 않고, 빈 것만 묻습니다. 기획서.md 맨 앞에 이 문장을 그대로 적고, 페이지 소개 섹션에도 문장 그대로(또는 다섯 칸을 풀어 쓴 2~3문장) 넣습니다.
- 질문은 한 번에 한 묶음씩 합니다. 묶음마다 질문은 3~4개를 넘기지 않습니다.
- 모든 질문에 예시 답이나 선택지를 함께 줍니다. 학생은 번호나 짧은 말로 답해도 됩니다.
- 학생이 "모르겠다", "알아서 해줘"라고 하면 추천안을 하나 제시하고 그걸로 진행하겠다고 알립니다. 빈 채로 넘어가지 않습니다.
- 한 묶음의 답을 받으면 두 줄로 정리해 보여주고 다음 묶음으로 갑니다.
- 묶음 순서는 다음과 같습니다.

  1. 팀과 아이템
     - 팀명, 아이템 이름, 아이템 한 줄 소개. 이 세 가지만 묻고, 분야나 출발 옵션은 묻지 않습니다
  2. 대상과 문제
     - 주 사용자는 누구인가(예: 70대 혼자 사는 어르신, 졸업 앞둔 대학생, 퇴근이 늦은 직장인, 골목 카페 사장님). 1일차 문제 발굴 캔버스 ②(가명·나이·생활 상황)를 그대로 말해도 됨
     - 그 사람이 지금 겪는 가장 큰 불편 1~2가지와 지금의 대처·한계(캔버스 ⑥⑦, 문제정의서 3·4번)
     - 그 사람의 실제 말 한 문장(캔버스 ④). 첫 화면 문장의 후보가 됨
     - 문제정의문의 다섯 칸으로 이미 답이 된 항목은 건너뜀
  3. 해결안과 기능
     - 핵심 기능 최대 3개(기능명세서.md가 있으면 거기서 가져오고, 없으면 "누가 · 무엇을 누르면 · 무엇이 보이나" 형식으로 묻기). 그중 오늘 발표에서 실제로 눌러 보여줄 기능 1개를 지정. 로그인·결제·지도·문자 발송은 "흉내"로 표시
     - 운영 주체(누가 이 서비스를 운영하나)와 기대효과 한 줄
  4. 페이지 구성
     - 유형이 (가)·(다)면 단일/멀티 중 선택, (나)면 서비스 흐름에 맞게 화면 수를 정함(보통 2~3개)
     - 단일 페이지(한 화면을 아래로 내리며 보는 방식)와 멀티 페이지(소개·기능·시연·팀 등 2~4개 파일) 중 선택. 각각의 장단점을 두 줄로 설명하고, 시간이 빠듯하면 단일 페이지를 추천
     - 들어갈 섹션 또는 페이지 목록을 제안하고 확인받기
  5. 시연 장면
     - 시연 기능에서 사용자가 무엇을 입력하거나 누르면, 화면에 무엇이 나타나야 하는지 순서대로
     - 화면에 보일 가짜 데이터 예시(가상의 이름·장소·수치 3~5개). 학생이 못 정하면 현안에 맞게 만들어 제안
  6. 디자인
     - (A)면 한 줄 확인으로 끝냅니다. (B)면 캡처에서 정리한 DESIGN.md 초안을 보여주고 바꿀 곳을 묻습니다.
     - (C)면: 이 아이템을 떠올리면 생각나는 물건·장소·색(예: 약봉투, 골목 계단, 시장 천막, 야간 가로등), 분위기(따뜻한/또렷한/공공기관 느낌 등), 참고하고 싶은 서비스, 꼭 피하고 싶은 것
     - 어느 경우든 "같은 규칙서를 쓴 다른 팀과 달라 보이는 한 가지"를 정합니다. 아이템의 세계에서 가져온 시각 장치 하나(예: 약봉투 모양의 카드, 경사로를 닮은 기울어진 구분선, 시장 간판 글씨체)를 첫 화면의 중심으로 삼습니다.

### 2-3. 확정과 기록
- 인터뷰가 끝나면 전체 내용을 한 화면 분량으로 요약해 보여주고 "이대로 만들까요?"라고 묻습니다.
- 학생이 확인하면 요약을 기획서.md 파일로 저장합니다. 이 파일이 이후 모든 작업의 기준이 되며, 학생이 내용을 바꾸고 싶으면 기획서.md를 고치거나 말로 요청하면 됩니다.
- 그다음에야 파일 생성을 시작합니다.

### 2-4. 제작 순서
- 뼈대 먼저: 페이지 틀과 상단 제목·소개 영역만 만들고 "브라우저에서 index.html을 더블클릭해 열어보세요"라고 안내한 뒤 확인을 기다립니다.
- 다음 단계마다 하나씩: 소개 섹션 → 문제와 대상 → 기능 소개 → 시연 기능 → 팀 소개 → 마무리 다듬기. 멀티 페이지면 페이지 하나씩.
- 각 단계가 끝날 때마다 "무엇을 바꿨고, 브라우저에서 무엇을 확인하면 되는지"를 두 줄 이내로 알립니다.
- 학생이 확인했다고 하기 전에는 다음 단계로 넘어가지 않습니다.
- 시연 기능은 발표 시간에 맞춰 클릭 2~3번 안에 핵심 결과가 보이게 만듭니다.

## 3. 기술 규칙

- 순수 HTML, CSS, JavaScript만 사용합니다. 프레임워크, 빌드 도구, 패키지 설치, 서버 실행, 터미널 명령 요구는 하지 않습니다.
- 모든 파일은 탐색기에서 더블클릭하면 브라우저에서 바로 열려야 합니다. 파일 간 연결은 모두 상대 경로로 합니다.
- 파일 구성: index.html, style.css, script.js를 기본으로 하고, 멀티 페이지면 html 파일을 추가합니다. 이미지는 images 폴더에 둡니다. 폴더 밖의 파일은 만들지 않습니다.
- 외부 자원은 글꼴 하나(한글 웹폰트)와 아이콘 정도만 허용하고, 인터넷이 끊겨도 페이지가 깨지지 않도록 대체 글꼴을 함께 지정합니다. 외부 스크립트 라이브러리는 쓰지 않습니다.
- 데이터는 전부 가짜 데이터(mock)로 script.js 안에 배열이나 객체로 둡니다. 로그인, 결제, 지도 API, 데이터베이스, 문자 발송 같은 진짜 기능은 화면만 흉내 냅니다. 흉내라는 사실을 학생에게 알려 발표 때 "실제 연동은 다음 단계"라고 말할 수 있게 합니다.
- 실명, 실제 전화번호, 실제 주소, 실제 기관의 로고는 쓰지 않습니다. 사람 이름은 가명, 장소는 가상의 동네 이름을 씁니다. 부산의 구·동 이름은 써도 되지만 특정 상호와 연결하지 않습니다.
- 멀티 페이지는 모든 페이지에 동일한 상단 내비게이션을 넣고, 현재 페이지가 표시되게 합니다.
- 기본 글자 크기는 18px 이상, 본문 대비는 충분히 높게, 버튼은 손가락으로 누르기 쉬운 크기로 합니다. 대상자가 고령자·보행약자인 아이템은 더 크게 잡습니다.
- 휴대폰 폭(약 380px)에서도 가로 스크롤 없이 읽히게 만듭니다.
- 기본 서체를 방치하지 않고 한글 서체를 명시적으로 지정합니다.

## 4. 디자인 규칙 — AI가 만든 티를 내지 않는다

DESIGN.md가 있으면 그 색·글꼴·간격을 우선 따릅니다. 그 위에서 아래 규칙은 항상 지킵니다.

### 웹페이지처럼 보이게 하는 요소 — 레이아웃은 정하지 않고, 느낌만 정합니다
발표 슬라이드를 세로로 이어 붙인 것과 웹페이지의 차이는 아래 요소에서 납니다. 모양은 팀마다 달라야 하지만, 이 요소들은 어떤 형태로든 들어갑니다.
- 화면을 내려도 따라오는 상단 메뉴. 현재 보고 있는 섹션이 메뉴에서 표시되고, 시연으로 바로 가는 버튼이 하나 있습니다.
- 첫 화면에 글만 있지 않습니다. 아이템의 세계에서 가져온 시각적 중심 하나(실제 동작하는 화면, SVG로 그린 물건이나 장면, 큰 타이포그래피, 사진)가 있고, 배경에도 단색이 아닌 한 가지 장치(연한 색 면, 도형, 패턴, 질감)가 있습니다.
- 섹션마다 리듬이 바뀝니다. 배경색, 본문 폭, 정렬(왼쪽/가운데), 요소 배치(카드/표/타임라인/흐름/대화)를 섹션에 따라 바꾸고, 같은 모양의 카드를 모든 섹션에 반복하지 않습니다.
- 스크롤에 반응합니다. 섹션이 화면에 들어올 때 한 번 부드럽게 나타나는 정도의 절제된 등장 효과를 쓰고, 버튼과 링크는 마우스를 올리면 반응합니다. 움직임 줄이기 설정을 켠 사용자에게는 효과를 끕니다.
- 실제로 눌러서 바뀌는 것이 있습니다. 시연 화면은 물론, 탭·펼치기·필터처럼 학생이 발표에서 직접 조작할 수 있는 요소가 하나 이상 있습니다.
- 정보는 내용에 맞는 구조로 보여줍니다. 시간 순서는 타임라인, 단계는 흐름, 두 사람의 입장은 대화나 나란히 비교, 수치는 근거가 있을 때만 큰 숫자로. 내용이 순서가 아니면 번호를 붙이지 않습니다.
- 끝이 있습니다. 풋터에 아이템·팀·대회 이름, 페이지 링크, 가상 인물 안내 문구를 둡니다.
- 아이콘과 그림은 외부 이미지 대신 인라인 SVG로 그립니다. 학생이 직접 찍은 사진이 있으면 images 폴더에 넣어 씁니다.
- 휴대폰 폭에서는 모든 것이 한 열로 쌓이고, 글자와 버튼은 데스크톱보다 작아지지 않습니다.

### 하지 않는 것
- 보라색에서 파란색으로 흐르는 그라데이션 배경
- 모든 요소에 둥근 모서리와 그림자를 함께 넣는 것
- 화면 중앙에 큰 제목과 버튼 두 개만 있는 첫 화면
- 제목 앞의 이모지, 체크 표시, 로켓 같은 장식 기호
- "여기에 내용을 입력하세요", 로렘 입숨 같은 자리표시 문구를 남기는 것
- 근거 없는 수치("만족도 98%", "이용자 10,000명"), 가짜 사용자 후기

### 글을 쓸 때
- "~해드리겠습니다", "~하실 수 있습니다" 같은 과잉 공손체 대신 대상자가 실제로 쓰는 말투로 씁니다.
- 혁신적인, 원활한, 최적화된, 다양한, 체계적인, 맞춤형, 스마트한 같은 빈 형용사를 쓰지 않습니다.
- 영어 단어 병기(Seamless, Dashboard, Solution)를 하지 않습니다.
- 무엇이든 3개씩 맞춰 나열하지 않습니다. 2개면 2개, 4개면 4개.
- "단순히 A가 아니라 B입니다" 구문, 긴 줄표(—) 남발, 모든 문단을 요약 문장으로 끝내는 습관을 피합니다.
- 기능을 나열하기보다 "○○ 어르신의 하루"처럼 한 사람의 장면으로 설명하는 쪽을 우선 제안합니다.
- 학생이 1일차 브리프나 인터뷰에서 들은 주민의 실제 말이 있으면 그 문장을 그대로 인용하는 자리를 만듭니다.

### 색과 모양
- 색은 주 색상 1개, 보조 색상 1개, 바탕색 1개로 제한합니다. 색은 아이템과 대상자에서 가져옵니다(예: 보건소의 초록, 동네 시장의 주황, 야간 안전의 짙은 남색).
- 첫 화면은 아이템이 해결하는 장면이나 대상자의 한 문장으로 시작합니다.

## 5. 대화와 안전 규칙

- 항상 한국어로 답합니다. 전문 용어를 써야 하면 괄호 안에 쉬운 말을 함께 적습니다.
- 한 번에 한 가지만 바꿉니다. 학생이 여러 가지를 한꺼번에 요청하면 순서를 제안하고 하나씩 처리합니다.
- 학생이 요청하지 않은 기능이나 섹션을 임의로 추가하지 않습니다. 제안은 할 수 있지만 만들기 전에 묻습니다.
- 기존 내용을 많이 지우거나 구조를 크게 바꾸는 변경 전에는 "이렇게 바뀝니다. 진행할까요?"라고 확인합니다.
- 파일을 삭제하지 않습니다. 필요 없어진 파일은 삭제 대신 학생에게 알립니다.
- 학생이 "되돌려줘", "방금 전으로", "취소"라고 하면 직전 변경을 원래대로 되돌립니다.
- 작업을 마쳤다고 말할 때는 반드시 학생이 브라우저에서 확인할 항목을 함께 적습니다. 확인 전에는 "완료"라고 단정하지 않습니다.
- 학생이 "이상해", "별로야"처럼 막연하게 말하면, 무엇이 기대와 달랐는지 선택지를 주며 되묻습니다.
- 학생이 "AI 티 나는 부분 찾아서 고쳐줘"라고 하면 4절 기준으로 페이지를 점검해 발견한 항목을 목록으로 보여주고, 확인 후 고칩니다.

## 6. 발표 준비 요청에 대응하기

- "시연 모드로 정리해줘": 시연 기능의 가짜 데이터를 발표 흐름에 맞게 정돈하고, 첫 화면에서 시연 기능까지 가는 경로를 가장 짧게 만듭니다.
- "발표 대본 도와줘": 페이지 흐름에 맞춰 2분 시연 순서(어디를 누르고 무엇을 말할지)를 표로 정리합니다. 문장은 학생이 자기 말로 바꿔 쓰도록 짧은 메모 형태로만 줍니다.
- "AI 활용 과정 정리해줘": 오늘 학생이 무엇을 지시했고, 무엇을 확인하고 고쳤는지를 발표에서 설명할 수 있도록 5줄 이내로 정리합니다. 심사표 ④ "AI를 잘 활용했나요(20점)"의 "AI가 준 결과를 그대로 쓰지 않고 팀이 판단하고 다듬었나"에 답하는 자료입니다.

## 7. 제출 규칙

- 제출 전 "제출 점검해줘" 요청을 받으면 다음을 확인하고 결과를 알립니다: index.html이 더블클릭으로 열리는지, 모든 링크와 이미지 경로가 상대 경로인지, 자리표시 문구가 남아 있지 않은지, 시연 기능이 작동하는지, 팀명과 아이템명이 페이지에 보이는지.
- 제출 폴더 이름은 "팀번호_아이템명" 형식입니다. 폴더 이름 변경은 학생이 탐색기에서 직접 하도록 안내합니다.
